# Тулчейн для «вайбкодинга» операционной системы

Главная идея: ИИ-агент должен иметь возможность **сам** собрать ОС, запустить её,
посмотреть лог и понять, удачно ли изменение. Весь тулчейн строится вокруг этого цикла.

## 1. Кросс-компилятор

**Рекомендация: LLVM/Clang + lld.**
- Один и тот же clang компилирует под любую цель флагами `-target x86_64-unknown-none-elf` —
  не нужно собирать отдельный кросс-GCC.
- `lld` умеет линковать ELF напрямую (`-fuse-ld=lld`), меньше боли с binutils.
- На macOS (включая ARM) работает из коробки: `brew install llvm lld`.
- Бонус: позже тем же clang собираем таргет для нашей ОС (лекция 16).

Альтернатива, если захочется классики: `x86_64-elf-gcc` (сборка Crosstool / homebrew-пакет).
Минус — долгая пересборка и отдельная дерево инструментов.

Базовые флаги ядра:
```
-ffreestanding -nostdlib -nostdinc -fno-stack-protector -fno-pic
-mno-red-zone -mcmodel=kernel -Wall -Wextra -O2 -g
```
`-g` обязателен: отладка ядра без отладочной информации — мазохизм.

## 2. Эмуляция и отладка

- **QEMU** (`qemu-system-x86_64`): стандарт эмуляции для хобби-ОС.
  - `--nographic` / `-serial stdio` — весь serial-вывод ядра в терминал;
    в headless-режиме: `-serial file:build/serial.log -display none`.
  - `-d int,cpu_reset -D qemu.log` — лог прерываний и ресетов, спасает при тройных fault'ах.
- **GDB** против QEMU: `-s -S` (QEMU ждёт GDB на :1234), дальше
  `gdb kernel.elf -ex 'target remote :1234'`. Работает и с LLVM-овским lldb.
- **Скрипт-обёртка** `scripts/debug.sh` — QEMU + GDB в одном окне, брейкпоинт на kmain.

## 3. Скрипты — «руки» агента

Всё, что агент может вызвать одной командой из корня репозитория:

| Скрипт           | Что делает                                                        |
|------------------|-------------------------------------------------------------------|
| `scripts/build.sh`  | Полная сборка: ядро → libc → userland → образ диска (hdd.img) |
| `scripts/run.sh`    | Сборка + запуск QEMU в интерактивном режиме (serial в терминал)|
| `scripts/test.sh`   | Сборка + headless QEMU + smoke-тесты; exit code 0/1            |
| `scripts/debug.sh`  | QEMU с GDB-сервером + готовый конфиг отладки                   |
| `scripts/mkfs.sh`   | Создать/обновить образ диска с ФС и userland-программами       |

`test.sh` — сердце вайбкодинга: запускает QEMU с `-serial file:`, ждёт маркеров в логе
(`[OK] boot`, `[OK] kthreads`, `[OK] first-user-elf` …), по таймауту — fail.
Агент: правит код → `build.sh` → `test.sh` → читает `build/serial.log` → чинит дальше.

## 4. Сборка образа

- Bootloader: **Limine** (протокол + бинарники ставится скриптом, без сборки UEFI-тулчейном).
- Диск: плоский образ `hdd.img`, FAT32 через `mtools`/`mkfs.fat` на хосте —
  без монтирования и прав, работает на macOS и Linux.
- Сборка через Makefile (цели all/kernel/clean/test) — Make есть у всех агентов «в крови».

## 5. Хост-машина разработчика (и агента)

- macOS / Linux: brew-пакеты `llvm lld qemu mtools make limine` (или выкачивание Limine).
- Python 3 — для утилит вокруг образа и для агента из лекции 19.
- Никаких облачных CI: весь «CI» — локальный `test.sh`, который гоняет те же сценарии.

## 6. Конвенции репозитория для агентов (AGENTS.md)

Ключевые правила, которые кладём в `AGENTS.md` в корне `os/`:
1. После любого изменения — `scripts/build.sh && scripts/test.sh`; не прошло — чини, не коммить.
2. Новый syscall: сначала запись в `docs/syscalls.md`, потом реализация в ядре, потом libc.
3. Запрещены silent-провалы: любая ошибка в ядре печатается в serial с контекстом.
4. Ассемблерные файлы менять только с объяснением каждого регистра в комментарии.
5. Не тащить код из Linux/BSD: лицензии + размер. Пишем сами или просим агента писать с нуля.
6. Именование веток, формат коммитов и pre-commit проверки — см. [CONTRIBUTING.md](CONTRIBUTING.md).

## 7. Pre-commit hooks (защита от ломающих коммитов)

Хук `.githooks/pre-commit` перед каждым коммитом запускает
`scripts/build.sh` и `scripts/test.sh`. Не прошло — коммит отменяется. Подключение:
`git config core.hooksPath .githooks`. Это наш «CI на коленке»: тот же набор проверок,
что гоняет ИИ-агент, просто обязан пройти каждый коммитящий. Подробности — в
[CONTRIBUTING.md](CONTRIBUTING.md).

## Итоговый цикл разработки

```
человек ставит задачу → агент правит код → build.sh → test.sh
   ↑                                                        │
   └── агент читает serial.log / gdb ←── fail ←─────────────┘
                                  └── pass → человек ревьюит дифф
```
